## Streaming vs batch

The streaming rows feed the same audio in 30 ms chunks — the daemon's own
preview tick — rather than handing over a finished file, so the per-call
cost the user actually waits through is inside these numbers.
**Time to first token** is what decides whether a model starts feeling
live; total time cannot tell you that, and neither can it tell you
whether the preview kept coming — see [Preview cadence](#preview-cadence)
below for that half of the answer.

Only models the catalog marks as streaming appear here. Whisper is absent
by architecture, not by omission: it is encoder-decoder over 30-second
windows and has no incremental decode to measure.

First token is measured from the first chunk, with the model already
loaded — a daemon holds it warm long before anyone speaks, so folding a
model load into this number would describe a wait no user experiences.
Load is in the JSON as `load_ms`, and in the totals.

| `fastconformer-streaming` | 363 ms | 7.69 s | 8.30 s | -611 ms |

| `nemotron-streaming-en-80ms` | 1.73 s | 27.21 s | 28.17 s | -968 ms |
| `nemotron-streaming-en-560ms` | 389 ms | 7.37 s | 7.90 s | -536 ms |

### Preview cadence

Time to first token says when the preview *starts*. It says nothing about
whether the text then flows or arrives in lumps — and that is the half a
user notices. An **update** is a chunk whose returned text differs from
the previous chunk's: one repaint of the overlay.

| Model | Updates | Mean gap | Longest gap | Slowest chunk |
|---|---:|---:|---:|---:|
| `fastconformer-streaming` | 72 | 256 ms | 960 ms | **96 ms** |
| `parakeet-unified-en-streaming-240ms` | 73 | 256 ms | 960 ms | **999 ms** |
| `nemotron-streaming-en-80ms` | 63 | 291 ms | 1.14 s | **186 ms** |
| `nemotron-streaming-en-560ms` | 26 | 700 ms | 1.14 s | **154 ms** |
| `nemotron-streaming-multi-560ms` | 30 | 607 ms | 1.14 s | **184 ms** |
| `zipformer-streaming` | 53 | 350 ms | 660 ms | **55 ms** |
| `zipformer-streaming-20m` | 50 | 366 ms | 960 ms | 21 ms |

**Mean gap** and **longest gap** are distances in *audio time* — position
in the stream — not wall clock. The harness feeds chunks as fast as the
recognizer accepts them, so a wall-clock gap would report how fast this
CPU is rather than how the model behaves, and would shrink on a faster
machine while the lumpiness a user sees stayed exactly the same. The wait
*before* the first update is excluded — that is first token, above — and
the silence *after* the last one is included, so a model that emits a few
partials early, goes quiet, and delivers the rest at the end of the
stream cannot score a clean mean.

**Slowest chunk** is the exception: it is wall clock, because it is the
longest single `FeedChunk` call and the daemon has only 30 ms before the
next chunk is due.

How to read the update count: it is repaints across the whole fixture, so
divide by the 20.0 s of audio. Three or four repaints a second reads as
continuous text appearing as you speak. A mean gap past about 500 ms does
not: the overlay sits still and then jumps a phrase at a time, which is
what a user reports as "it comes in chunks rather than continuously".
**Longest gap** is the worst of those freezes and is the number that
predicts the complaint — a healthy mean with a 1.3 s worst case still
feels to the speaker like the preview stopped.

> [!WARNING]
> **These models paint the preview in lumps, whatever their first-token
> figure says.** Do not pick one as `preview.source` on the strength of
> the latency table alone.
>
> - `nemotron-streaming-en-560ms` — 26 updates over 20.0 s of audio: a repaint
>   every 700 ms on average, with a longest freeze of 1.14 s. The overlay holds
>   still, then jumps a phrase at a time.
> - `nemotron-streaming-multi-560ms` — 30 updates over 20.0 s of audio: a repaint
>   every 607 ms on average, with a longest freeze of 1.14 s. The overlay holds

> [!CAUTION]
> **A bold slowest-chunk figure overran the daemon's 30 ms preview tick.**
> The daemon feeds the preview from a ticker on one goroutine, so a
> `FeedChunk` that takes longer than the interval cannot be absorbed:

> a slower CPU pushes more models over the line, and that is the point:
> it is measured where the daemon would run. `stream_slow_chunks` in the
> JSON says how many calls overran, which separates one hiccup from a
> model that can never keep up.

## Warm server vs cold CLI

`advanced.placement = "subprocess"` spawns `whisper-cli` per utterance and
reloads the model every time; the default placement for a whisper model
keeps a `whisper-server` child warm and posts the audio to it. The warm
column is the per-utterance time with the
model already resident. Startup is what the daemon pays once, at login,
and is excluded from it.

These rows drive `internal/speech`, the same client the daemon uses, so
what is measured is the code path a user gets rather than a stand-in.

| Model | Threads | Warm | Cold CLI | Saved | Startup | RTF |
|---|---:|---:|---:|---:|---:|---:|
| `whisper-tiny.en` | 6 | 564 ms | 814 ms | -250 ms | 102 ms | 0.028 |
| `whisper-base.en` | 6 | 1.03 s | 1.56 s | -533 ms | 101 ms | 0.052 |
| `whisper-small.en` | 6 | 3.30 s | 3.94 s | -634 ms | 151 ms | 0.165 |

A negative **saved** figure is the server winning. Peak memory is absent
from this table on purpose: the server is a long-lived child of the
harness rather than a process that exits per run, so the `getrusage`
high-water mark the memory table uses does not apply to it.

## How to rerun this

```console
$ just bench            # every backend: whisper on CPU, the in-process
                        # sherpa engines, and GPU if a Vulkan build is present
$ just bench-gpu-build  # build the Vulkan whisper.cpp the GPU column needs
```

Method, so a rerun elsewhere means the same thing:

- Each cell runs **3 times** and the report takes the **median**, not the
  mean (one scheduler stall would move a mean of three) and not the best
  case (nobody experiences the best case).
- Timings are **cold-start totals**: model load plus inference, which is
  what a user waits through. The `sherpa` rows break load out separately
  in the JSON, because a daemon that keeps a model warm pays it once.
- The filesystem cache is **warm** by the second run of each cell, and 3 of
  the runs see it warm. Treat the numbers as steady-state, not first-boot.
- The GPU column comes from an out-of-tree whisper.cpp built with
  `-DGGML_VULKAN=ON`. The CPU and GPU rows use **the same binary**,
  differing only in whisper.cpp's `-ng` flag, so the comparison isolates
  the backend rather than the build.
- Each sherpa model runs in its own **worker process**. sherpa-onnx
  reports a model it cannot load by aborting from C++ rather than
  returning an error, so without isolation one bad model would end the
  sweep and lose every result before it.
- Before publishing a GPU column the harness checks that the build
  actually loaded a GPU backend and that a Vulkan device enumerated. If
  either check fails it refuses the column and says so above, rather than
  reporting CPU numbers under a GPU heading.
